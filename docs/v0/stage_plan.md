# Linux 侧职责

RK3588 Linux 侧负责：

摄像头设备枚举；
V4L2 采集；
buffer 管理；
图像预处理；
RKNN Runtime 推理；
分割 mask 后处理；
足球中心点、半径、置信度计算；
dx/dy 偏差计算；
控制策略；
UART 控制帧发送；
MCU 状态帧接收；
视频或状态回传；
日志和测试数据保存。

Linux 侧不直接做硬实时电机控制。

# MCU/RTOS 侧职责

MCU/RTOS 侧负责：

UART 接收；
控制帧解析；
checksum 校验；
控制命令限幅；
RTOS task / queue 解耦；
PWM 输出；
舵机或电机控制；
限位保护；
急停处理；
失联保护；
云台状态回报。

MCU 侧不做 AI 推理，不做复杂图像处理，不做网络视频回传。

# PC 上位机职责

PC 上位机负责：

查看回传视频；
查看状态数据；
保存测试日志；
分析延迟、误差和追踪成功率。

第一版 PC viewer 可以非常简单，不做复杂 UI。

# 第一版通信方式

第一版选择 UART。

选择理由：

硬件连接简单；
Linux 和 MCU 都容易支持；
可用 USB-TTL 调试；
协议可控；
适合第一版验证控制闭环。

第一版暂不使用 CAN，除非 UART 抗干扰或线长明显不足。

# 关键技术风险
## 摄像头风险

风险：

/dev/videoX 不稳定；
摄像头格式不匹配；
fps 不足；
buffer 出队阻塞；
只用 OpenCV VideoCapture，缺少 V4L2 证据。

规避策略：

第一版优先 USB UVC 摄像头；
V2 必须保存 v4l2-ctl 输出；
V2 必须实现或明确计划 V4L2 mmap 采集；
先验证 fps，再接模型。

降级方案：

分辨率降到 640x480；
fps 降到 15；
先保存单帧和 fps 日志；
暂不做实时预览。

## RKNN 推理风险

风险：

模型无法转换；
输入输出不清楚；
量化后效果下降；
推理耗时过高；
后处理无法得到稳定中心点。

规避策略：

优先选已有 ONNX 模型；
V3 单独验证 RKNN 推理；
V4 单独验证 mask 到中心点；
不把模型效果和控制闭环混在同一阶段调试。

降级方案：

先用静态测试图；
先用低分辨率输入；
先用非量化 RKNN；
如果分割模型不稳定，临时使用颜色球或简单检测模型验证控制链路，但最终报告必须说明这是阶段性替代方案。

## Linux → MCU 通信风险

风险：

串口丢包；
帧解析错位；
dx/dy 越界；
通信频率过高；
急停命令不可靠。

规避策略：

设计帧头、长度、类型、checksum；
控制量使用限幅；
MCU 收不到命令时进入安全状态；
区分控制帧和状态帧；
每条命令带 timestamp 或 sequence id。

降级方案：

先只发固定 pan/tilt 命令；
再发送 dx/dy；
先 10 Hz 控制频率；
暂不加 CAN。

## 云台控制风险

风险：

云台抖动；
方向反了；
舵机超限；
控制过冲；
MCU 死机后云台失控。

规避策略：

先用舵机；
加 dead zone；
加限幅；
加失联保护；
加急停；
加机械限位或软件限位。

降级方案：

只做单轴 pan；
降低控制频率；
使用固定步进控制；
先不做 PID，只做比例控制。

## 视频/状态回传风险

风险：

视频编码耗时高；
网络延迟高；
上位机 viewer 不稳定；
视频和状态时间戳不同步。

规避策略：

MVP 可先回传状态 JSON/CSV；
视频可先用 MJPEG/TCP；
每帧带 frame_id 和 timestamp；
V8 再考虑 RTSP/GStreamer/H.264。

降级方案：

先只回传状态；
再回传低 fps JPEG；
再做 MJPEG；
最后考虑 RTSP。
